# 任务：My Agent 的【设置】模块与个人数据归属设计

> 2026-11-09 修订：**不做 Workspace / 团队空间 / 多租户**。本应用定位为**个人助手**，一个账号对应一个人，所有数据归属该账号（或其名下的 Agent），不存在「团队资源」这一层。
> 账号与鉴权（users / sessions / Cookie 会话 / 数据隔离）已于 2026-11-09 实现并上线，方案见 [`auth.md`](auth.md) 与 [ADR-0008](adr/0008-auth-and-session.md)。**本文档只描述尚未实现的部分**：设置模块本身，以及模型配置、数据导出等与账号相关的待办。

请基于当前项目的实际代码、技术架构和需求文档，设计【设置】模块及其背后的数据归属规则。

## 一、设计目标

应用支持两种运行模式，且两者共用同一套业务模型：

1. **Local**：本机单用户，无需注册即可用，数据落在本机 MySQL（当前默认形态）。
2. **Cloud**：部署到服务器，多账号注册登录、跨设备访问、数据按账号隔离（当前已实现的形态）。

两种模式只在「身份来源」和「配置来源」上有差异：Local 可以自动登入一个本机内置账号，Cloud 走邮箱注册登录。**业务表、接口、前端页面完全复用一套。**

## 二、需要设计的内容

### 1. 设置模块（本期主要交付）

设置页要解决「用户能在应用里改哪些东西」，首版范围建议如下（待确认拍板，见 §四）：

- **模型接入**：provider（fake / openai 兼容）、Base URL、API Key、模型名、超时。
- **账号资料**：邮箱（只读）、显示名、改密码。
- **登录设备**：当前账号的会话列表（设备、IP、最近活动、过期时间），可撤销单个或全部其他设备。
- **数据管理**：导出全部对话（JSON / Markdown），清空全部对话，注销账号（连带数据清理）。
- **外观**：明暗主题、字号（如果做）。
- **关于**：版本号、接口健康状态、许可证。

不在本期范围：Workspace、成员邀请、角色权限（Owner/Admin/Member）、计费。

### 2. 数据归属

逐个明确下列数据属于 **User**、**Agent**、**Conversation** 还是 **System**（本应用没有 Workspace）：

| 数据 | 归属 | 现状 |
|---|---|---|
| 用户资料（邮箱、显示名、密码哈希） | User | ✅ 已实现 `users` |
| 登录会话（token 哈希、设备、过期） | User | ✅ 已实现 `sessions` |
| 用户设置（模型配置、外观偏好） | User | ❌ 待设计：新建 `user_settings` 表还是并入 `users` 列 |
| 模型 API Key | User | ❌ 待设计：**必须加密存储**，不能明文落库 |
| 对话与消息 | Conversation（经 `user_id` 归属 User） | ✅ 已实现 `conversations.user_id` |
| Agent 定义（名称、System Prompt、模型） | Agent（经 `user_id` 归属 User） | ❌ 阶段 5 之后 |
| Memory / RAG 知识库 | User | ❌ 阶段 8 |
| 文件与附件 | User | ❌ 未规划 |
| Skill / MCP Server / 工具权限 | User | ❌ 阶段 7 |
| 定时任务、执行记录、用量统计 | User | ❌ 未规划 |
| 模型列表、公告、健康检查 | System | ✅ 无需归属 |

### 3. 权限与隔离

- 个人助手**不需要 RBAC**；只保留一个二元角色：`user`（普通）与 `admin`（可看运维信息、可关闭注册），已有 `users.role` 字段。
- 所有私有资源必须验证归属，**归属只在 service 层强制**，越权一律返回 404（不暴露资源是否存在）。
- Agent 的工具调用必须由后端校验身份上下文，不允许依赖 System Prompt 做权限控制。
- 异步任务 / 子 Agent 必须显式传递 `user_id`，不允许从全局状态推断。

### 4. Local 与 Cloud 的差异

| 维度 | Local | Cloud |
|---|---|---|
| 身份来源 | 自动登录本机内置账号（首次启动创建） | 邮箱 + 密码，服务端会话 Cookie |
| 数据库 | 本机 MySQL / 容器卷 | 托管 MySQL |
| 配置来源 | `.env` 优先，设置页写入的覆盖 `.env` | 设置页写入（按账号） |
| API Key | 可继续放 `.env`，也可在设置页填 | 必须加密存库，按账号隔离 |
| 迁移与同步 | 手动导出/导入 JSON | 跨设备自动可见 |

### 5. 数据库设计

优先复用现有模型（`users`、`sessions`、`conversations`、`messages`），新增表时给出字段、索引、外键与迁移方案；不要重复创建已有结构。

### 6. 安全设计

- 密码哈希：Argon2id（已实现）。
- 会话：库中只存 token 的 SHA-256；HttpOnly + SameSite=Lax Cookie；30 天滑动续期（已实现）。
- **API Key 加密**：需确定方案（对称加密 + 主密钥来自环境变量；或暂不落库、仅支持 `.env`）。
- 越权防护、账号删除时的数据清理（`ON DELETE CASCADE` 已覆盖会话与对话）。
- 设置页里展示 API Key 时必须脱敏（只显示末 4 位）。

## 三、设计原则

1. 不过度设计，不提前实现企业级能力（团队、权限矩阵、计费）。
2. 个人用户必须简单：不需要理解任何「空间/组织」概念。
3. 为未来多账号、多设备、自建 API 接入做合理预留。
4. 身份、权限和数据归属由后端确定性逻辑保证，不依赖提示词。
5. 不擅自重构已有 Agent 核心架构。

## 四、输出成果

先输出方案，本阶段不改代码：

1. 设置模块的信息架构与页面清单（含空态、错误态、保存中态）。
2. 设置数据模型：`user_settings` 表结构（或复用 `users` 的取舍理由）+ 迁移方案。
3. 接口契约：读写设置、导出数据、注销账号（含错误码与权限）。
4. API Key 存储方案对比（加密落库 vs 只读 `.env`）与推荐。
5. Local / Cloud 两种模式的启动与登录流程图。
6. 与现有 `auth.md` / ADR-0008 的关系（哪些结论不变，哪些要补充）。
7. 迭代计划：哪些进本期 T-FE-02，哪些留到后续阶段。
