# ADR-0005 测试基线：后端覆盖率门槛 + 前端 api 层单测

- 状态：已采纳（2026-11-07）
- 相关：[ADR-0002 前端质量门禁轻量档](0002-frontend-quality-gate-lite.md)、[TECHNICAL_DEBT T-04](../project/TECHNICAL_DEBT.md)

## 背景

在排期第 5 项「测试基线」之前，测试只有一层：后端 25 个用例全部停在参数校验与异常处理，
服务层（真正写 SQL 的部分）零覆盖；前端完全没有单测，只有 18 项 E2E 与人工验收。

问题不是「测试少」，而是**测试的形状不对**：

- 后端最常出 bug 的地方是 services（分页、筛选、删除保护、局部更新），而它们一行都没被跑过；
- 前端最容易静默出错的是 `src/api` 的错误映射（422 详情拼接、网络异常文案、业务 code 兜底），
  这类逻辑在浏览器里要构造异常才能看到，人工验收基本覆盖不到。

E2E 能兜住主流程，但它需要 MySQL + 后端 + 浏览器，跑一次一分多钟，不适合当每次提交的闸门。

## 决策

1. **后端加覆盖率门槛**：`pytest-cov`，`fail_under = 80`，`omit` 掉 `app/init_db.py`、`app/seed.py`
   （只有 `__main__` 入口的手工脚本）。当前实测 85%（分母 383 行）。
2. **服务层用内存 SQLite 测**，不引入 MySQL/容器：`StaticPool` + `sqlite+pysqlite:///:memory:`，
   每个用例建表、结束即销毁。测的是 SQL 语句与业务分支，不是 MySQL 方言。
3. **前端加 Vitest，只测 `src/api`**：`environment: node`，不引 jsdom；用 axios 自定义 adapter
   造响应，`vi.mock` 掉 `element-plus` 的 `ElMessage`。不写组件快照，不设覆盖率门槛。
4. **CI 各加一步**，其余不动：后端 `uv run pytest`（门槛生效）、前端 `pnpm test`。

## 代价

- SQLite 与 MySQL 有方言差异，因此**明确不测**：唯一键 `1062` 分支、外键约束报错、`utf8mb4` 排序；
  这几处仍只有人工与 E2E 兜底（T-04 只算部分解决）。
- 内存 SQLite 的建表来自 `Base.metadata`，与迁移脚本是两条路径；模型改了但迁移忘改时，
  测试照样绿。防线仍然是 `make check-migration`（需要真实数据库）。
- 前端单测只覆盖 api 层，`views`/`components` 的行为只能靠 E2E，组件重构没有安全网。
- 85% → 80% 留了 5 个百分点的余量：写新代码时不至于为了凑数字去写无意义断言，但也意味着
  「不写测试」最多只能撑 5 个百分点就会被门禁拦住。

## 被否方案

| 方案 | 否掉的原因 |
| --- | --- |
| testcontainers 起真实 MySQL | 每次跑测试要拉镜像、等健康检查，本地和 CI 都变慢；与「轻量档」取向冲突 |
| 用生产 `fastapi_demo` 库跑测试 | 会污染演示数据，且 CI 无法提供数据库 |
| 前端用 jsdom + @vue/test-utils 写组件测试 | 组件测试维护成本高、断言脆；现有 18 项 E2E 已覆盖主交互 |
| 覆盖率设 100% 或按文件卡门槛 | 收益低、噪声大；异常分支的成本远高于其价值 |
| 用 Playwright 替换 puppeteer 作为唯一测试层 | 仍需完整后端与数据库，无法作为每次提交的快速闸门（见 ADR-0002 已暂缓） |

## 复评触发条件

- 出现一次「SQLite 能过、MySQL 失败」的真实事故 → 引入 testcontainers 的 MySQL 用例集；
- 后端新增的 service 代码量超过现有 services 总和 → 把门槛提到 85%，并按模块设门槛；
- 前端 `src/api` 出现第三类逻辑（如手写重试、缓存）→ 补对应单测，或评估引入 MSW 做请求级测试；
- CI 总时长超过 3 分钟 → 把前端单测与后端测试拆到不同 job 并行（当前串行够用）。
