# ADR-0015 聊天消息流投影与稳定执行项

- 日期：2026-11-18
- 状态：已接受
- 相关方案：[聊天整理第二步](../chat.md#9-聊天状态与展示一条时间线2026-11-18--11-19)

## 背景

实时过程挂在用户消息后，完成后历史过程挂在助手消息前；即使位置相同，两条模板分支仍会重建组件，导致已展开的过程与单条详情折叠。页面同时读取消息、回放缓存和实时状态，容易重复渲染正文。

## 决定

- 纯函数 `buildChatFeed` 将当前会话数据投影为普通消息项与执行项，不复制可写业务状态，不发请求。
- 发送前建立本地展示 key，记录到对应运行；正式用户/助手消息 ID 替换不改变执行项 key。key 带会话作用域，刷新后的历史运行使用运行 ID。
- 执行项优先放在已加载助手消息的位置并消费该正文；无助手消息时放在用户消息后。当前页没有锚点的待审批或实时项仍保留入口，其他页的已完成项不显示。
- `ChatMessageList` 按 key 渲染，`ChatExecutionItem` 复用一个时间线组件，并以互斥分支交接正式与流式正文。现有 details 节点保留两层展开状态，不另建展开状态缓存。

## 取舍与边界

仅调整模板位置无法保持组件身份；强制按用户消息渲染会在消息分页缺少用户消息时丢失执行项，因此采用纯投影。组件不增加布局容器或视觉规则。

第二步实施时暂时保留两套步骤状态；后续 [ADR-0016](0016-chat-execution-state-and-recovery.md) 已统一执行状态和请求生命周期。路由与滚动提取仍待后续步骤。本次不要求跨浏览器刷新保存展开状态；刷新创建新组件并按需加载历史详情。

## 验证

投影测试覆盖唯一正文、多个运行、分页与 key 连续性；页面测试验证从临时 ID、流式正文到完成和历史核对期间的组件及详情节点身份。真实 Chrome 使用模拟事件点击展开两层详情，检查完成后仍展开且正文只有一份。测试数量与检查结果以项目状态为准。
