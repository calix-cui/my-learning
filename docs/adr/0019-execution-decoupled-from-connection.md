# ADR-0019 执行与连接解耦：运行活在自己的线程里，连接只是订阅

- 状态：已接受
- 日期：2026-11-19
- 关联：[ADR-0016](0016-chat-execution-state-and-recovery.md)（断流后的执行状态）、[ADR-0018](0018-reconnect-contract-and-read-only-polling.md)（断线核对契约；本 ADR 取代它「不做真续跑」的结论）

## 背景

用户刷新页面这个动作，会让正在生成的回答彻底消失。原因不是前端丢了内容，而是**服务端把执行停了**：

- `agent/executor.py` 的 `stream_run` 是一个生成器，它**就是**执行循环（`yield from _run_loop(...)`）；
- 它跑在请求线程里，`api/sse.py` 的 `encode_sse` 在 `finally` 里关闭事件生成器；
- 于是 `GeneratorExit` 沿着 `_relay_preview` → `_run_loop` → `stream_run` 的 `finally` 一路抛出，上游 httpx 连接被关闭（`with closing(...)`），模型停止生成，`_finish_interrupted_run` 把运行标成 `failed("运行被中断")`。

`agent_runs` 里因此只有用户消息，正文一个字都没有——因为它只活在 `openai_compatible.py` 里 `pieces` 这个局部变量中，`"".join(pieces)` 在流正常结束之后才执行。

用户提出的判断是行业约定：**运行的生死与某一次 HTTP 连接的生死无关**。主流 Agent 后端都这样处理——OpenAI Responses API 的 background 模式先返回 id、后台执行、按 id 读取或取消；ChatGPT 网页关掉后回复仍在生成；Codex 的 CLI 与 Web 共用同一份会话与运行；Temporal 一类 durable execution 把「运行状态 + 事件历史」落库，客户端只是重放者。

同时，现有实现已经证明「运行可以跨请求存活」是可行的：审批挂起（`waiting_approval`）后连接结束，批准时 `resume_run` 从 `agent_steps` 重放上下文接着跑。本 ADR 把这个能力从「审批专用」推广到「所有连接中断」。

## 决定

### 1. 运行是持久对象，执行在后台线程

新增 `agent/hub.py`：`RunHub` 登记每条运行的事件出口（`_Channel`），把循环交给守护线程跑，线程自己开 `SessionLocal()`、自己解析模型与工具。

接口层只做两件事：`prepare_run` 校验并落库（404/400/409 仍是普通 JSON），然后 `run_hub.start_new_run(...)` 拿到订阅。**请求线程不再承载执行**，客户端断开只会少一个订阅者。

线程自己管 Session 是必须的：SQLAlchemy Session 不是线程安全的，且请求依赖在响应结束时就会关闭会话。

### 2. 先落库再转发：正文按快照写入 `agent_runs.draft_content`

执行线程每 500ms 或每累积 200 字，把「本轮已生成的正文」写进 `agent_runs.draft_content`；本轮正常结束、正式助手消息落库后清空该列。工具步骤仍逐条写 `agent_steps`（已有行为）。

不做逐 token 入库：重连只需要「看到已生成的部分」，不需要逐字回放动画；逐 token 会把一次回答变成几百次 UPDATE。

### 3. SSE 降级为纯读取，支持 `since_seq` 回放

新增 `GET /api/agent/runs/{run_id}/stream?since_seq=N`：先回放库里已有的（`draft_content` + `seq > N` 的步骤），再挂到订阅队列 tail 到终态。订阅者可以来多个、可以中途加入、可以随时离开，彼此不影响。

同一个运行的订阅是纯读操作，不产生副作用。

### 4. 断连不等于取消；取消是显式接口

连接断开只注销订阅者，不改变运行状态。取消由 `POST /api/agent/runs/{run_id}/stop` 触发：置 `stop_reason='user_cancelled'`，在下一个检查点关闭上游生成器，把已生成正文落成助手消息并标 `cancelled`。

「连接断开」不再产生 `failed("运行被中断")`。`_finish_interrupted_run` 保留，但它现在只服务三种情况：用户停止、进程退出、进程崩溃后的启动清理。

### 5. 终止后的消息形态

被用户终止的回答保留已生成正文，页脚显示「您终止了此次会话」，后面跟一个「重新生成」按钮（刷新图标 + 文字，样式复用现有次级按钮 token，不新增组件）。

点「重新生成」= **删除旧回答，完全重新生成**：删除旧助手消息及其运行记录，用同一条用户消息、新的 `request_id` 新建一次运行。用户明确要求不留旧内容，因此这是唯一的破坏性操作，且只作用于「运行产出的助手消息」，不会触碰用户消息。

### 6. 无人订阅 10 分钟后停止

订阅者数量归零时记录 `orphaned_at`；持续 10 分钟仍无人订阅且不在等审批，则停止并标记 `failed("长时间无人接收，已停止")`。期间只要有人重新订阅，计时清零。

判定不能用「瞬时订阅数为 0」：刷新页面时旧连接先断、新连接后连，中间必然有一个空窗。订阅是否还在，靠两层检测——SSE 生成器的 `finally`（客户端断开时必然执行）与 15 秒心跳写入失败；静默消失（拔网线、休眠）只能靠后者发现。

### 7. 同一会话保持串行

第二次提交仍返回 409。现有上下文重放假设步骤按顺序追加，放开并发要先设计交错上下文，不在本次范围内。

### 8. 单进程边界

`RunHub` 是进程内的对象，订阅请求必须落到持有这次运行的进程。当前部署是单进程（`scripts/dev.sh` 的 `uvicorn`，无 `--workers`），本 ADR 把「单进程」从隐含假设变成明确约束：多 worker 部署前必须先做跨进程广播（Redis pub/sub 或任务队列）。这条记在技术债 T-30。

### 9. 本次不做

- 跨进程广播、运行队列与并发控制；
- 断点「续跑」（不需要了：不停就不存在续）；
- 逐 token 回放；
- 纯文本（非 agent）流式接口的解耦，它没有工具与审批，等第 1–8 条稳定后再说。

## 后果

**正面**

- 刷新、断网、关标签页都不再丢正在生成的回答；回来能看到完整过程与结果。
- 「重复提交」问题消失：同一条运行可以反复订阅，不需要重发。
- 断线核对契约（ADR-0018）从「事后核对」升级为「继续观看」，`request_id` 认领退化为兜底。
- 服务端第一次真正拥有「正在进行的任务」这个对象，后续的排队、限流、多端观看都有了挂点。

**负面**

- 没人看也照样烧 token——用「无人订阅 10 分钟」止损。
- 每条运行占用一条数据库连接与一个线程；连接池默认 15，因此并发上限按 4 规划。
- 进程重启仍会中断正在跑的运行（启动清理负责收尾），真正的重启不丢属于任务队列的范畴。

## 验证

- `backend/tests/test_run_hub.py`：订阅晚到能补历史、订阅者离开后执行继续、读太慢的订阅者被踢掉、`inline` 模式同步跑完。
- `backend/tests/test_agent_api.py`：既有 18 项覆盖创建、审批、回放、断线核对的契约不变。
- `frontend/scripts/chat-live-acceptance.mjs`：真实模型下刷新页面后正文继续增长（第 4 条决定的可观测证据）。
