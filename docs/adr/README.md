## 什么时候写 ADR

- 决定「以后不能轻易改」的东西：技术栈、数据格式、部署形态、目录边界。
- 决定**不做什么**同样值得写（例如「暂不引入 Playwright」），否则半年后会被重新讨论一遍。
- 一次选型如果有多个候选，把落选者的「放弃理由」写清楚，比只写结论更有价值。

## 什么时候不用写

- 库的小版本升级、局部重构、样式调整。
- 还没决定的事——写进 `PROJECT_STATUS.md` 的「待决策」即可，别用 ADR 假装已决策。

## 约定

- 文件名：`NNNN-kebab-case-title.md`，编号递增不复用。
- 状态：`提议` / `已接受` / `已废弃`（废弃的保留文件并注明替代者）。
- 决策变更不删旧文件，新增一条 ADR 并在旧文件头部标注 `被 ADR-XXXX 取代`。
