# ADR-0011 工具权限分级与人工审批

> **AI 向文档**：本文是给 AI 协作者的决策记录。人读入口见 [`docs/README.md`](README.md)。

- **状态**：提议（待确认）
- **日期**：2026-11-10
- **相关**：[ADR-0010](0010-agent-execution-loop.md)（执行循环）、[`docs/tools.md`](../tools.md)（本阶段设计）

## 背景

阶段 5 的执行循环允许模型直接调用工具，工具集只有三个只读工具（`calculator` / `now` / `search_conversations`），所以「模型自己决定执行」是安全的。阶段 6 要引入写操作与外网调用，风险性质变了：

- 写操作（改标题、删会话、改设置）**不可逆**或**影响用户数据**；
- 外部调用会带出用户数据、也可能被提示注入利用；
- 一旦出事，当前只能看到「某个 run 失败了」，没有「谁批准了什么」。

三条可选路线：① 不做分级，靠提示词约束模型；② 只做白名单（默认禁用一切写工具）；③ 分级 + 人工审批。

## 决策

采用 **③ 分级 + 服务端持久审批**，具体六条：

1. **工具按风险分三级**：`read`（自动）、`write`（审批）、`external`（审批 + 出站白名单）。默认由级别推出是否需要审批，可显式覆盖。
2. **审批状态是服务端的持久资源**（新表 `agent_approvals`），不是进程内事件。run 挂起时状态写库，恢复时从 `agent_steps` 重放上下文。
3. **审批只对「决定」负责，不伪造结果**：批准才真正执行工具；拒绝则回灌一条「用户拒绝，理由：…」的 `tool_result`，让模型换路。
4. **审批不限时**：状态在 DB，页面一直等用户回复（快模型慢用户是常态，超时判失败等于白跑）。用「次数上限」代替「时间上限」：单次 run 最多 5 次审批、同一工具最多被拒绝 2 次。
5. **参数级规则独立于级别**：黑名单/上限（如指数过大、字符串过长）在进入审批前直接拒绝，减少无效审批。
6. **工具来源抽象为 `ToolSource`**：内置、MCP（阶段 7）、未来的插件都从同一注册表进入，执行器不认识具体工具。

## 代价

- 执行器要支持「暂停 → 恢复」，`stream_run` 不再是纯同步生成器，恢复路径要单独测（客户端断流、进程重启、审批超时三种都要覆盖）。
- 多一张表、多一个状态值（`waiting_approval`），前端时间线与审批卡片要处理交叉状态。
- 审批会打断对话节奏：用户可能觉得麻烦。缓解是「只对写/外网要求审批」，读工具永远直跑。
- 审计数据随时间增长：随 run 级联删除，后续可按天归档。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| 只靠提示词约束（「不要删除数据」） | 提示注入可绕过；出错无法追责；与 AGENTS.md「不允许隐藏异常制造假成功」相悖 |
| 白名单：默认禁用一切写工具 | 功能价值归零，用户想用还得改代码；也无法表达「这次允许」 |
| 审批状态放进程内存（`asyncio.Event` / `input()`） | 重启、多 worker 部署必丢；uvicorn `--workers 2` 时批准请求可能落到另一个进程 |
| 审批严格超时（如 10 分钟） | 用户离开一会儿就白跑一次运行；先做「不限时 + 次数上限」，靠清理任务兜底长期挂起的 run |
| 直接引 LangGraph 的 `interrupt()` | 为一个人工审批引一整套图编排，与 ADR-0010「自研约 250 行循环」的取舍冲突；我们的状态在 MySQL，本来就能恢复 |
| 审批结果由客户端回传「已批准」 | 服务端无法验证；等价于把授权判定交给前端 |

## 复评触发

1. 出现「同一类审批每天超过 20 次」→ 需要「记住这个工具/参数的决定」规则（当前明确不做）。
2. 引入多 agent 或后台异步任务 → 审批要支持「没有在线用户」的异步通知（邮件/IM），当前只做在线弹窗。
3. 工具数量超过 15 个或需要按组织授权 → 引入角色-权限矩阵（当前只有 user/admin）。
4. 审批误放行导致数据损坏事故 → 重新评估「写操作默认需审批」是否要升级为「写操作默认禁用 + 显式授权」。
