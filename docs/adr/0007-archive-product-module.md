# ADR-0007 归档商品管理模块并更名为 My Agent

> **AI 向文档**：架构决策记录，人与 AI 共读；每条决策的「为什么」是重点。总入口见 [`../README.md`](../README.md)。

- 状态：**已采纳**
- 日期：2026-11-08
- 相关：[PROJECT_STATUS §1](../PROJECT_STATUS.md)、[`archive/product-admin/`](../../archive/product-admin/README.md)、[ADR-0006](0006-llm-client-and-chat-storage.md)

## 背景

阶段 1–3 交付的是「商品管理后台」：商品 / 分类 CRUD + 概览 + 18 项验收。阶段 4 起，项目真正的主线是 AI Agent 应用（对话已经能接 DeepSeek 跑通）。

两套东西同时留在默认路径上有三个实际成本：

1. **认知成本**：新读者打开仓库先看到 3 个商品页面和 11 个商品/分类接口，会以为这是一个 CRUD 练习项目，找不到 Agent 主线。
2. **维护成本**：每次改工程化（lint、测试、CI、依赖、目录）都要同时处理商品模块；它的测试（43 例）占后端用例的 36%，却与后续阶段无关。
3. **风险成本**：商品代码里的 MySQL 1062 错误码判断、`decimal(8,2)` 序列化等细节继续被文档引用，会把「历史实现」误当成「当前约定」。

同时项目名 `product-admin` 已经名不副实。

## 决定

1. **整体归档，不删除**：商品 / 分类 / 概览的前后端代码、需求（PRD）、设计稿与规格、验收记录、实机截图、旧 API 契约，全部 `git mv` 到根级 `archive/product-admin/`，保留 git 历史。
2. **应用层只留对话**：`backend/app` 只注册 `/api/conversations`（订单式分层不变），`frontend` 只有 `/chat` 一个页面，`/` 与其它的路由一律重定向到 `/chat`。
3. **数据库移除两张表**：新增迁移 `17fe0c7d2cb5` 删除 `products` 与 `categories`（先子表后父表），downgrade 按原结构重建。**数据会丢**，这是有意为之——归档代码仍可从 `archive/` 恢复到任何库。
4. **更名 `my-agent`**：前端包名、页面标题、Compose 项目名（`name: my-agent`）、默认库名（`my_agent`）统一改；本地库通过 dump + 导入迁到 `my_agent`，`backend/.env` 指向新库。
5. **文档按新边界重写**：`docs/api.md` 只保留对话与探针（旧契约存档到 `archive/product-admin/docs/api-product-admin.md`），`how-it-works` / `toolchain` / `PROJECT_STATUS` / `README` / 角色卡同步。

## 代价

- 归档代码不会被 CI、lint、测试覆盖，会**随时间腐化**；如果真的要恢复，需要重新接依赖与测试。
- 删表迁移不可逆（数据层面），只能靠备份或 `downgrade` 重建空表。
- Compose 项目名改变后，命名卷从 `product-admin_db-data` 变成 `my-agent_db-data`，旧容器数据不会自动挂载；本轮数据本来就在本地库，影响可忽略。
- 文档里仍会出现「商品 / 分类」字样（历史记录、归档目录说明、ADR-0003 的背景），需要读者分辨「现状」与「历史」。

## 被否方案

| 方案 | 为什么没选 |
|---|---|
| 保留商品模块，仅新增 Agent 页面 | 主线被稀释；每轮工程化都要维护两套；用户明确要求「全部弃用」 |
| 直接删除商品代码 | 丢失可复用的 CRUD 范本（分层、分页、校验、错误映射），与「优先复用」原则冲突 |
| 保留商品接口只删前端 | 后端仍要维护 11 个与主线无关的接口、43 个用例与对应文档 |
| 用 feature flag 关掉商品路由 | 代码仍在主路径，lint / 测试 / 认知成本一点没省 |

## 复评触发

1. 阶段 6（Tool Calling）需要一个「能被 Agent 调用的 CRUD 工具」时——可参考归档实现，但应作为新工具重写，而不是恢复旧表。
2. 需要演示「多模块微服务」形态时。
3. 归档代码出现安全漏洞（补丁只改归档不现实，届时应彻底删除）。
